# Lessons

## Fabric: Eventstream Lakehouse destination

- **Small files are a setting.** DOCUMENTED ([Learn](https://learn.microsoft.com/fabric/real-time-intelligence/event-streams/add-destination-lakehouse)): Advanced > *Minimum rows* (1 to 2 million per file) and *Maximum duration* (1 min to 2 h per file). Larger values give fewer, bigger files; still run `OPTIMIZE`.
- **Schema comes from the first record.** DOCUMENTED (same page): a new table takes its schema from the first event; later extra fields are dropped, missing ones become null. Send a stable shape.
- **Events before routing starts can be lost.** DOCUMENTED (same page): uncheck *Activate ingestion*, publish, then resume with a custom earlier start time.
- **The writer rejects table features.** OBSERVED 2026-10-28: a table pre-created by Fabric Spark (deletion vectors on by default, so protocol 3/7 with `invariants`, `deletionVectors`…) failed every write: "Table has unsupported features. Unsupported writer features: invariants". Pre-create with `delta.enableDeletionVectors = false, delta.minReaderVersion = 1, delta.minWriterVersion = 4` (v4 is the lowest that allows Change Data Feed); the writer then appends and CDF by commit version returns every row (`nb_setup_lakehouse`, `nb_check_bronze_trades`).
- **Commits come every ~2 min, not every *Maximum duration*.** OBSERVED 2026-10-28: with `maximumDurationInSeconds: 900` and `minimumRows: 2000000` the destination still committed every ~2 min. Expect small files; `OPTIMIZE`.
- **An ISO 8601 string doesn't convert to a `TIMESTAMP` column.** OBSERVED 2026-10-28 (`nb_check_es_types`, one probe event per case): events with `"2026-10-28T15:15:10.708706Z"` or `"…+00:00"` in a field whose Bronze column is `TIMESTAMP` were dropped (`OutputDataConversionError.TypeConversionError`); events with only strings, bigints and floats (including `4.3712e-06` and `80395.0`) landed. A single such field drops every event, so the table gets no commit at all. Keep time fields as `STRING` in Bronze and cast in Silver.
- **Dropping the destination table deactivates the destination.** OBSERVED 2026-10-28: after `DROP TABLE` and `CREATE TABLE`, the Lakehouse destination went inactive until reactivated in the portal; `CREATE OR REPLACE TABLE` left it `Running`. But a running destination keeps the column types it read at start: after `CREATE OR REPLACE` changed `_load_ts` from `TIMESTAMP` to `STRING`, every event was still dropped until the destination was paused and resumed (`startType: CustomTime` to replay what was sent meanwhile). After any change to the table's columns, restart the destination.
- **CDF can't be read across a schema change.** OBSERVED 2026-10-28: `table_changes` from version 1 to 3 of `bronze.trades` failed with `DELTA_CHANGE_DATA_FEED_INCOMPATIBLE_DATA_SCHEMA` because version 2 was a `CREATE OR REPLACE` that changed column types. Start CDF reads after the last `CREATE`/`REPLACE` commit (`nb_check_bronze_trades`); after a Bronze schema change, reset the Silver watermark (ADR 0002) to that version.
- **Dropping the destination table deactivates the destination.** OBSERVED 2026-10-28: after `DROP TABLE` and `CREATE TABLE bronze.trades` (`nb_setup_lakehouse`), the Lakehouse destination went inactive and nothing landed (table stayed at version 0); reactivating it in the portal fixed it. After recreating a destination table, reactivate the destination, with a custom start time if events sent meanwhile must land.

## Fabric: Eventstream HTTP source

- **The connection must be type `WebForPipeline`.** OBSERVED 2026-10-28: `RestService` and `HttpServer` connections fail import with "Error converting value … to type ExtensionDataSourceKind". `WebForPipeline` (Anonymous) works. The definition has no path field: the connection's `baseUrl` is the full endpoint (e.g. `https://api.kraken.com/0/public/Trades`); query parameters go in `requestParameters`.
- **A JSON array response becomes one event per element.** OBSERVED 2026-10-28: a JSON array response landed as one row per element, none as an array.
- **`fab import` works despite the CI/CD caveat.** DOCUMENTED ([Learn](https://learn.microsoft.com/fabric/real-time-intelligence/event-streams/add-source-http)): the HTTP source "doesn't support CI/CD features… might result in errors"; OBSERVED 2026-10-28: create through `fab import` succeeded.
- **No WebSocket source.** DOCUMENTED ([Learn](https://learn.microsoft.com/fabric/real-time-intelligence/user-flow-2)): the source list has HTTP, Kafka, MQTT, Pub/Sub, CDC…, no WebSocket; a WebSocket feed needs a collector sending to a custom endpoint.

## Fabric: Eventhouse and the hot path

- **Spike 5: a shortcut made by the Items API never became an external table.** OBSERVED 2026-10-29 (`eh_trades`, issue #13): `POST …/items/{kqlDb}/shortcuts` with `path: "Shortcut"` (not `Shortcuts`; the API only allows the folders `Tables`, `Shortcut`, `Context`, `SystemContext`) returned 201 and the shortcut listed, but `.show external tables` stayed empty for 7+ minutes and `external_table('dim_pair')` failed. The portal creates shortcuts differently ([Learn](https://learn.microsoft.com/fabric/real-time-intelligence/onelake-shortcuts)). Fallback in use: `.create-or-alter external table dim_pair kind = delta (h@'https://onelake.dfs.fabric.microsoft.com/<ws>/<lakehouse>/Tables/gold/dim_pair;impersonate')`, which reads fine (`Shortcut: false`). Not tried: creating the shortcut in the portal.
- **No query acceleration on that external table, so an update policy can't read it.** OBSERVED 2026-10-29: `.alter external table dim_pair policy query_acceleration '{"IsEnabled": true, "Hot": …}'` returned HTTP 400 with no detail for every `Hot` (1 d, 3650 d, 36500 d). DOCUMENTED ([Learn](https://learn.microsoft.com/kusto/management/update-policy?view=microsoft-fabric#query-limitations)): an update policy may call `external_table()` only on a table with acceleration on and `Hot` ≥ 100 years, and a `join` there needs streaming ingestion off on the source table. So `whale_trades` is filled by the threshold alone and `tracked_whale_trades()` applies the tracked-pair rule at read time; a materialized view can't read external tables either ([Learn](https://learn.microsoft.com/kusto/management/materialized-views/materialized-views-limitations?view=microsoft-fabric)), so `rtd_trades_live` filters `volume_5m` at query time.
- **`.execute database script` returned an opaque 400; the same commands one by one worked.** OBSERVED 2026-10-29. `scripts/kql-run.py mgmt` splits a `.kql` file on blank lines and runs each command in order. A bare `General_BadRequest` / `BadRequest` with no inner message is all Eventhouse says for a refused command, so bisect.
- **Eventstream → Eventhouse works with `ProcessedIngestion` from a definition.** OBSERVED 2026-10-29: the destination (`dataIngestionMode`, KQL database ID as `itemId`, `databaseName`, `tableName`, JSON `inputSerialization`) went `Creating` → `Running` in about 4 min and events landed in `trades_raw` ~24 s after they were sent, with `ingestionbatching` set to 10 s. `DirectIngestion` needs a data connection that only the portal can create (DOCUMENTED, fabric-skills `EVENTSTREAM-AUTHORING-CORE.md`).
- **Importing a stale `es_trades` file removes destinations other sessions added.** OBSERVED 2026-10-29: `fab import` replaces the whole definition, and destinations in `Creating` are not in a repo copy. Run `fab export` of the live item, change it, then import.
- **Real-Time dashboard `visualOptions` are schema-checked by the portal, `fab import` is not.** OBSERVED 2026-10-29: `xColumn: {"type": "infer"}` imported fine but the portal rejected it ("must be string,null"; `yColumns` and `seriesColumns` "must be array,null"). Use `null`, `null` and `["symbol"]`.
- **An Activator email goes only to an address inside the tenant.** DOCUMENTED ([Learn](https://learn.microsoft.com/fabric/real-time-intelligence/data-activator/activator-limitations)): each recipient must be in the creator's domain or a verified domain of the Entra tenant; external and guest addresses are not allowed. OBSERVED 2026-10-29 (`act_whale_trades`, issue #13): rules mailing `gmail.com` addresses produced no email after a whale event reached `tracked_whale_trades()`; a rule mailing `stu.ptit.edu.vn` made Activator send an error email, "Invalid Recipient Domain: The notification recipient has an invalid email domain", so the rule ran and the action was refused. The agent can't read a rule's history, and the service principal can't list workspace role assignments or tenant domains, so it can't check a recipient itself. Ask the owner for the UPN they sign in to Fabric with (avatar menu in the portal) and use that.
- **`/v1/rest/query` can return a transient 520.** OBSERVED 2026-10-29: `print 1` failed once with "Request aborted due to an internal service error", then succeeded on retry.
- **`trades_raw` keeps one day, so a day's hot totals need their own view.** DOCUMENTED ([Learn](https://learn.microsoft.com/kusto/management/materialized-views/materialized-view-policies?view=microsoft-fabric)): a materialized view has a retention policy independent of its source table. `hot_daily` (events and notional per pair and UTC day, `softdelete = 30d`) is what `nb_reconcile_hot_gold` reads; it holds only what `trades_raw` had when it was created plus everything since (created `async` with `backfill = true` on 2026-10-29, ready within a minute). The retention command for a view is `.alter-merge materialized-view <name> policy retention …` and fails with `BadRequest_EntityNotFound` while an `async` create is still running.
- **A notebook run by the service principal reads Eventhouse with `getToken('kusto')`.** DOCUMENTED ([Learn](https://learn.microsoft.com/fabric/data-engineering/notebookutils/notebookutils-credentials#get-token)) and OBSERVED 2026-10-29 (`nb_reconcile_hot_gold`, `fab job start`): `POST <queryServiceUri>/v1/rest/query` with that token returned `hot_daily` rows. The `kqlDatabases` Items API gives `queryServiceUri` but no `databaseName`: a query names the database by its display name (`eh_trades`).

## Source: Kraken spot WS v2 `trade` and REST `/0/public/Trades`

- **WS and REST describe the same trades.** OBSERVED 2026-10-28 (45 s on `BTC/USD`, `ETH/USD`, `DOGE/USD`): 145 trades in both had the same `trade_id`, price, qty, side (`buy`/`sell` vs `b`/`s`) and order type (`limit`/`market` vs `l`/`m`). REST rows are arrays `[price, volume, time, side, ord_type, misc, trade_id]` with price and volume as strings and time as epoch seconds (float).
- **`side` is the taker's.** DOCUMENTED ([Kraken](https://docs.kraken.com/api/docs/websocket-v2/trade)). Coinbase's `matches` uses the maker's side instead.
- **`trade_id` counts up by one per pair.** OBSERVED 2026-10-28: 1,000 consecutive REST trades on each of 4 pairs had no jump; `BTC/USD` starts at `trade_id` 1 (2013). Docs say only "unique per book", so treat contiguity as observed, not guaranteed.
- **Full history over REST.** OBSERVED 2026-10-28: `since=1` returns the first `BTC/USD` trades of 2013. `since` is epoch nanoseconds; `count` ≤ 1,000; the response's `last` is the next `since`. Rate limits not checked yet.
- **REST `since` is inclusive and `last` is a string.** OBSERVED 2026-10-29 (`BTC/USD`): calling with `since` = the previous `last` returns that last trade again at the top of the page, so a page after the first holds one new trade fewer; `last` comes back as a string of nanoseconds; a `since` past the newest trade returns an empty list and echoes `since` as `last`. `nb_backfill_trades` drops repeats by `trade_id` and stops on a page with nothing new. The REST `time` has about 7 decimals (`1761700003.6602204`); Bronze keeps microseconds, like the WS timestamp.
- **Pair names.** OBSERVED 2026-10-28: REST `Trades` accepts the WS v2 name (`pair=BTC/USD`) and returns it as the result key; `AssetPairs` still lists legacy names (`XXBTZUSD`, wsname `XBT/USD`, `XDG/USD`). Use WS v2 names everywhere.
- **Subscribe snapshot.** DOCUMENTED (same page): `snapshot: true` sends the last 50 trades per pair, `type: snapshot`; they can predate a REST window, so dedupe on (`symbol`, `trade_id`).
- **Status message lists maintenance.** OBSERVED 2026-10-28: the first `status` message carries `upcoming_maintenance` (spot REST and WS down ~15 min); expect a reconnect then.
- **A Fabric Python notebook holds the WS.** OBSERVED 2026-10-28 (`nb_check_kraken_ws`, 20 pairs, 6 min): one connection, no errors, longest silence 1.2 s (heartbeats), 2,947 trades, no `trade_id` jump on any pair, snapshot of 50 per pair. `websocket-client` is not preinstalled; the notebook installs it from code. Longer runs not tested yet.

## Fabric: notebooks

- **`spark.read.option("wholetext", True).text(path)` returned one line.** OBSERVED 2026-10-28 (`nb_build_dim_pair`, pretty-printed JSON in `Files/`): `.first()[0]` was `{`, so `json.loads` failed with "Expecting property name… line 1 column 2". Read a whole small file with `open("/lakehouse/default/Files/<path>")` instead.
- **A failed notebook run's `failureReason` carries no traceback.** OBSERVED 2026-10-28: only `System_Cancelled_Session_Statements_Failed`. Write the traceback to `Files/checks/` from a try/except (as `nb_check_*` do) to see it.
- **The SQL analytics endpoint lags new tables.** OBSERVED 2026-10-28: `gold.dim_pair` was `Invalid object name` right after creation; read the table through a notebook or `fab table schema` meanwhile.

- **A `%run` line in a `.py` notebook has no `# MAGIC` prefix.** OBSERVED 2026-10-29: `fab import --format .py` turned `# MAGIC %run nb_x` into the cell `%run nb_x%run nb_x`, so the job failed with "Cannot read notebook nb_x%run nb_x"; a plain `%run nb_x` line is stored and exported as written (only cell magics such as `%%configure` use `# MAGIC`). Find a hidden cell error by calling the notebook with `notebookutils.notebook.run` inside try/except from a throwaway notebook and writing the traceback to `Files/checks/`.
- **`%run` shares variables both ways.** DOCUMENTED ([Learn](https://learn.microsoft.com/fabric/data-engineering/author-execute-notebook)): all variables of the referenced notebook are available in the caller. A caller can set a flag before the `%run` and the referenced notebook can read it with `globals().get(...)` (`nb_test_load_silver` sets `library_only`).

- **`%run` also runs the referenced notebook's parameters cell.** DOCUMENTED (same Learn page as the `%run` variables note above; not observed): all variables are shared, so a notebook that `%run`s `nb_load_gold` would see its own parameter (e.g. `fact_table`) reset to `nb_load_gold`'s default. Name the caller's parameters differently (`mlv_source_table`).
- **A notebook run by a service principal can create and refresh an MLV.** OBSERVED 2026-10-29 (`pl_process_gold`): `CREATE MATERIALIZED LAKE VIEW IF NOT EXISTS … AS SELECT …` followed by `REFRESH MATERIALIZED LAKE VIEW … FULL` ran in a pipeline Notebook activity as the service principal. The pipeline's own Refresh Materialized Lake View activity does not support a service principal and refreshes every MLV of the lakehouse (DOCUMENTED, [Learn](https://learn.microsoft.com/fabric/data-factory/refresh-materialized-lake-view-activity)).
- **`agg_pair_daily` (open/close by `min_by`/`max_by`) refreshes incrementally only when `fact_trade` is partitioned by `trade_date`.** DOCUMENTED ([Learn](https://learn.microsoft.com/fabric/data-engineering/materialized-lake-views/refresh-materialized-lake-view)): aggregates other than `SUM`, `MIN`, `MAX`, `COUNT` need every source table partitioned and the partition column in `GROUP BY`. OBSERVED 2026-10-29 (`nb_test_refresh_agg_pair_daily`, 3.6 M synthetic rows in scratch tables `test.pt_*`, run as the service principal): unpartitioned, every refresh that had new trades was a `WRITE` Overwrite of all 220 MLV rows; with `PARTITIONED BY (trade_date)` it was a `MERGE` of only the affected rows (20 for an hour of today's trades, 1 for a late trade), and the MLV matched the direct `SELECT` every time. With nothing new neither wrote a commit. Refresh time did not differ (65 to 125 s either way, start-up dominates at this size). A plain `REFRESH MATERIALIZED LAKE VIEW x` (no `FULL`) ran the optimal strategy; `notebookutils.lakehouse.refreshMlv` does not exist in the notebook runtime. `min_by(price, struct(trade_ts, trade_id))` breaks ties on equal timestamps by `trade_id` (`nb_test_load_gold`).
